## 本轮修复的问题

### 1. 出厂配置里的通讯录 ID 会被 Secret 的旧值覆盖

**现象**：新部署设备装上包后没进「仁和堂门店」通讯录。

**根因**：出厂配置整体存在 GitHub Secret 里。Secret 最后更新于 10-27，
里面还是 `addressBookCollectionId = 1`（默认通讯录）；仓库里的
`deploy/store_config.json` 早已改成 3，但它是 `.gitignore` 忽略的文件，
CI 根本看不到 —— 打包时以 Secret 为准，打出来的包一直带着旧值。

**修复**：拆成两层，各管各的：

| 内容 | 存放位置 | 改一次的影响 |
|---|---|---|
| apiServer / userId / collectionId | 仓库 `deploy/store_settings.json`（版本化） | 提交即生效 |
| adminToken | GitHub Secret `STORE_ADMIN_TOKEN` | 改 Secret 即生效 |

CI 打包时把两者合并，不再有「两边不同步」的可能。

同时客户端内置兜底值也从 1 改成 3（`flutter/lib/store_config_service.dart`），
即使出厂配置文件缺失，也不会回落到默认通讯录。

### 2. base64 传参导致整个 Windows 构建失败

**现象**：CI 在 `Prepare store config` 步骤失败，报
`Only base64 data is allowed`，Windows x64 EXE 作业整个作废（耗时约 50 分钟）。

**根因**：Secret 里存的是 base64 文本，该文本在 CI 环境下被改写，
`base64.b64decode(..., validate=True)` 拒绝非 base64 字符。本地复现正常，
说明改写发生在传输途中。

**修复**：管理员令牌本身是纯 hex（`123456789abcef` 这类），
改用独立 Secret `STORE_ADMIN_TOKEN` 以明文注入，不做任何编解码，
穿过任何环境都不会变形。

## 门店端行为

1. 首次启动弹出门店名录入框。
2. 录入后写入 `store_user_config.json`（%APPDATA%\RustDesk\config\），
   并同步服务端 `peer.alias`。
3. 设备自动加入「仁和堂门店」通讯录（collection_id=3），无需手动添加。
4. 门店端名称被改动时自动纠正回服务端，保持本地名称为准。
5. 启动 60 秒后补偿同步一次，之后每 30 分钟自愈一次。
