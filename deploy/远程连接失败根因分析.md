# 远程连接失败根因分析（Failed to secure tcp: deadline has elapsed）

> 分析时间：2026-10-28　客户端版本：v1.5.1-custom（仁和堂定制版）
> 结论：**RustDesk 官方已知缺陷**，服务端 hbbs 未实现客户端要求的密钥协商握手。

## 一、现象

- 通讯录能同步（门店名能写入服务器）
- 远程连接失败：`Failed to secure tcp: deadline has elapsed: 请稍后再试`
- **登录了 API 的客户端连不上，没登录的能连**

## 二、根因（已由官方 PR #706 确证）

rustdesk-server **PR #706**（*"Implement server-side secure_tcp key exchange for hbbs"*）：

> *"Fixes a real, reproducible cause of **"Failed to secure tcp: deadline has elapsed"**:
> **hbbs never implements the server side of the secure_tcp handshake the client already speaks.**
> Any client whose ID-server connection falls back to TCP hangs forever waiting for a
> KeyExchange hbbs never sends."*

**机制**：客户端连上 ID 服务器后**不发送任何消息**，等服务器主动下发 `KeyExchange`。
而 hbbs 从未实现服务端这一半 —— 它在等客户端先说话。**双方互等，18 秒超时**（`READ_TIMEOUT = 18_000`）。

**为什么登录 API 才触发**（`src/client.rs:860`）：

```rust
let legacy_secure = !key.is_empty() && (!token.is_empty() || !switch_code.is_empty());
```

- `token` = API 登录后的 `access_token`
- `key` 恒非空（配置的 `key` 选项，或编译内置 `RS_PUB_KEY`）

没有 token → 不走 `secure_tcp` → 直接打洞 + 中继 → **成功**。
有 token → 走 `secure_tcp` → 撞上缺失的握手 → **失败**。

**双重死锁**：直连前要 `secure_tcp`（`client.rs:888`），**请求中继前也要**（`client.rs:1809`）
→ 有 token 时两条路都被堵死，中继请求根本发不出去。

PR #706 下另一位用户的场景与本项目完全一致：

> *"rustdesk-server 1.1.16 with **lejianwen/rustdesk-api v2.7** for a shared address book.
> **As soon as a client signs in**, every connection fails with `Failed to secure tcp: deadline has elapsed`."*

**三要素全中**：API v2.7（`/api/version` 返回 `2.7`）+ 服务端 1.1.16 + 登录 API。

## 五、修复方案

### 已实施：客户端降级（`7025cd9`）

`src/common.rs` 的 `key_exchange`：

1. 服务器**沉默**（超时）→ 视为「该服务器不做握手」→ 明文继续，不再报错
2. 只容忍**沉默**。回复到达但**验签不过**仍报错（那可能是中间人）
3. 首次探测只等 **3 秒**（支持的服务器建连后立刻就发），并按服务器地址**缓存**结果，
   后续连接 **0 等待**

**安全性影响**：只影响**客户端 ↔ ID 服务器**这一段（承载 ID 查询与打洞协调）。
**客户端 ↔ 被控端的会话仍是端到端加密的**（peer 连接有独立的密钥交换），
因此不会触发「不安全连接」提示框，**门店机可无人值守使用**。

### 备选：给 hbbs 打 PR #706 补丁（服务器端，最彻底）

在服务器上按 PR #706 给 hbbs 补上服务端握手（~80 行，改 `rendezvous_server.rs`），
需要 Rust 工具链。补丁作者已验证可用。

### 临时：门店机不登录 API

清空 `access_token` 即可跳过握手。**门店机不需要登录 API** 就能被远程连接，
所以这条对门店机是可接受的（代价：通讯录同步失效，门店名仍存本机）。

## 六、服务器环境隐患（与本次故障无关，但需处理）

服务器是 **Docker 部署**（`/www/dk_project/dk_app/dk_rustdesk/` 下有 `docker-compose.yml` 和 `.env`）：

1. **`hbbs -r {SERVER_IP}:21117`** —— `{SERVER_IP}` 是**未替换的占位符**，
   中继地址靠客户端配置的 `relay-server` 覆盖才正确
2. **`hbbr` 启动时没有 `-k` 参数**，hbbs 也没显式指定密钥
3. **密钥目录**：`/www/dk_project/dk_app/dk_rustdesk/data/`（含 `id_ed25519`、
   `id_ed25519.pub`、`db_v2.sqlite3`）—— **丢失则所有客户端都要重配**
4. 之前 `/usr/bin/hbbs` 二进制被删（进程还在内存里跑），说明环境管理不规范
