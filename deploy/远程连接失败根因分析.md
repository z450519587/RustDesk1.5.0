# 远程连接失败根因分析（Failed to secure tcp: deadline has elapsed）

> 分析时间：2026-10-28　客户端版本：v1.5.1-custom（仁和堂定制版）

## 一、现象

- 通讯录能同步（门店名「郑玉清」能写入服务器）
- 但远程连接失败，报 `Failed to secure tcp: deadline has elapsed: 请稍后再试`
- 办公室内网能连，出了公司网络必连不上

## 二、先排除的可能（都已实测排除）

| 怀疑 | 实测结果 | 结论 |
|---|---|---|
| 客户端代码被我改坏 | 10-27 11:37 就有同样错误，那时我还没动任何代码 | ✗ 排除 |
| 公网入口不通 | TCP 21116 / 21117 / 21114 全部可连 | ✗ 排除 |
| 公网入口不是同一台 hbbs | 用真实 RegisterPk/RegisterPeer 协议探针对比内网与公网，**响应行为完全一致** | ✗ 排除 |
| 出厂配置写错 | 已从安装包提取 `store_config.json`，md5 一致，API 地址 = `rd.renhetang.cn:21114` | ✗ 排除 |
| 客户端没注册到 ID 服务器 | API 显示设备在线，`updated_at` 实时刷新 | ✗ 排除 |
| 网络/NAT 问题 | 内网同局域网对端能成功建立中继 | ✗ 排除 |

## 三、根因

### 触发条件

客户端代码 `src/client.rs`：

```rust
// 860 行
let legacy_secure = !key.is_empty() && (!token.is_empty() || !switch_code.is_empty());
...
// 888 行：直连前的密钥协商
if !exchanged && legacy_secure {
    secure_tcp(&mut socket, &key).await.map_err(|e| anyhow!("Failed to secure tcp: {}", e))?;
}

// 1810 行：请求中继前的密钥协商
if !key.is_empty() && (!token.is_empty() || !switch_code.is_empty()) {
    secure_tcp(&mut socket, key).await?;
}
```

`token` 的来源（`src/ui_session_interface.rs:1984`）：

```rust
let token = LocalConfig::get_option("access_token");  // 登录 API 后的会话令牌
```

`key` 的来源（`src/common.rs:2074`）：配置的 `key` 选项，为空时回落编译内置的
`RS_PUB_KEY = "VQMjLpbApV6OgRkm1Ur0r5kEb8UkBhDZTCOm1r9IPyI="`（恒非空）。

### 双重死锁

**只要登录了 API（`access_token` 非空），两条路都被堵死：**

1. 直连协商 → `secure_tcp` 超时 → 报错退出
2. 请求中继 → 中继请求**之前**也要 `secure_tcp` → 同样超时 → 中继请求根本发不出去

### 超时的原因

`secure_tcp` → `key_exchange`（`src/common.rs:2222`）：

```rust
match timeout(READ_TIMEOUT, conn.next()).await? {   // READ_TIMEOUT = 18_000
```

客户端连上 ID 服务器的 TCP 后**不发送任何消息**，纯粹等服务器主动下发
`KeyExchange`。服务器 18 秒不下发 → 超时。

实测失败间隔与 `READ_TIMEOUT = 18_000` 完全吻合。

### 为什么无 token 时能成功

10-27 11:44 那次成功的日志：

```
[11:44:57] #1 TCP punch attempt with 192.168.1.104:32532, id: 25721967
[11:44:57] relay requested from peer, time used: 62.0251ms, relay_server: 60.213.11.2:21117
[11:44:57] 5.7474ms used to establish Relay connection
```

当时 `access_token` 恰好为空 → `legacy_secure = false` → 完全跳过 `secure_tcp`
→ 打洞 + 中继直接走通。

**规律**：唯一成功的一次，是唯一 `access_token` 为空的一次。

## 五、待确认的一环（需要服务器权限）

`secure_tcp` 能否成功，取决于 **hbbs 是否用与客户端内置 `RS_PUB_KEY` 对应的私钥签名**。

客户端内置的服务器公钥（编译进二进制，不可改）：

```
VQMjLpbApV6OgRkm1Ur0r5kEb8UkBhDZTCOm1r9IPyI=
hex: 5503232e96c0a55e8e811926d54af4af99046fc5240610d94c23a6d6bf483f22
```

**在服务器上执行**：

```bash
cat /opt/rustdesk-server/id_ed25519.pub
```

- 若输出**一致** → 公钥没问题，那问题在 hbbs 版本太老、不支持新版的
  KeyExchange 协议（客户端是 1.5.x 新版，会主动要求服务器先做密钥协商），
  → **升级 hbbs 到与客户端匹配的版本**
- 若输出**不一致** → 客户端内置的公钥与服务器实际公钥不匹配
  → **用服务器的 id_ed25519.pub 重新编译客户端**（替换 `config.rs` 的 `RS_PUB_KEY`）

## 六、临时规避办法（不需重编译）

清空 `access_token` 即可跳过 `secure_tcp`：

```powershell
# 备份
Copy-Item "$env:APPDATA\RustDesk\config\RustDesk_local.toml" "$env:APPDATA\RustDesk\config\RustDesk_local.toml.bak"
# 清空
$p = "$env:APPDATA\RustDesk\config\RustDesk_local.toml"
$t = Get-Content $p -Raw -Encoding UTF8
$t = $t -replace "(?m)^access_token\s*=\s*'[^']*'", "access_token = ''"
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($false)))
```

⚠️ 代价：客户端无法登录 API，**通讯录同步会失效**（门店名仍可保存在本机）。
门店机不需要登录 API 就能被远程连接，所以对门店机是可接受的临时方案。
（本机测试已清空并验证配置生效，备份在 `RustDesk_local.toml.bak-token-test`）

## 七、根本修复方向（三选一）

1. **升级 hbbs** 到与 1.5.x 客户端匹配的版本（最正确，需服务器权限）
2. **重新编译客户端**，把 `RS_PUB_KEY` 换成服务器实际的 `id_ed25519.pub`
3. **改客户端逻辑**：让 `secure_tcp` 失败时降级为「不加密」而非直接失败
   （安全性下降，不推荐，但能立刻恢复可用性）
