## 🔴 严重：管理员令牌明文提交进了公开仓库

**现象**

管理员令牌 `<旧令牌>` 以明文出现在两个已跟踪的
markdown 文档里：

| 提交 | 文件 | 行 |
|---|---|---|
| `3fbd878` (10-26) | `deploy/门店名称同步部署说明.md` | 57 |
| `e514735` (今天) | `deploy/门店端最终交付说明.md` | 45 |

仓库 `z450519587/RustDesk1.5.0` 的可见性是 **public**，
`git log -S "<令牌>"` 能直接翻出这两个提交。

**为什么严重**

这个令牌等同于**服务器管理员权限**（可读写 peer 表与 address_book 表）。
之前我们花力气用 libsodium sealed box 加密 Secret，正是为了不让它明文外泄；
结果它从另一个门（文档）走了出去。

讽刺的是，`deploy/store_sync_token.sql` 里我们自己写的建议第 4 条就是：
「**不要**把含真实 token 的 store_sync.json 提交进 Git 仓库」。
文档类文件同样适用。

**修复（已完成部分）**

- 两处文档里的令牌已替换为占位符 `<管理员令牌，见 deploy/store_config.json 或联系管理员>`
- 当前工作区与已跟踪文件中已无该令牌（脚本逐文件复查确认）
- 新写的轮换脚本与本报告本身也做了打码 —— 否则「写修复脚本」这个动作
  会把令牌再写进一次历史，等于自己给自己制造新泄露

**修复（待执行，必须做）**

git 历史无法真正抹除 —— 删文件、改历史都只是「让搜索变难」，
有心人照样能翻出来。**唯一彻底的补救是让旧令牌失效**。

已备好 `deploy/rotate_admin_token.sql`，步骤是：

1. 用管理员账号登录 API 后台，拿到新令牌 `NEW_TOKEN`
2. `UPDATE user_tokens SET expired_at = 253402300799 WHERE token = 'NEW_TOKEN';`
3. `DELETE FROM user_tokens WHERE token = '<旧令牌>';`
4. 本地改 `deploy/store_config.json` → `python deploy/update_store_secret.py` → 推送触发构建
5. 新包分发到门店机（覆盖安装，门店名不会丢 —— 它存在 `%APPDATA%` 而非安装目录）

> 旧包在换包前门店名同步会失败（远程连接不受影响）。

## 🟠 中等：HTTP 请求完全没有超时

**现象**

`store_sync_service.dart` 里两处 `HttpClient()` 都没有设置任何超时：

```dart
final client = HttpClient();
client.badCertificateCallback = (cert, host, port) => true;
// 没有 connectionTimeout，没有 idleTimeout
```

Dart 的 `HttpClient` 默认**连接和读取都不超时** —— 服务器不响应时，
请求会无限期挂起。

**实际后果（两个）**

1. **首启弹窗卡死**：门店点「保存并同步」后，`syncStoreName` 内部会
   轮询等待 peer 上线（最长 5 分钟），期间 UI 卡在 loading 态。
   而这个弹窗**不可关闭**（`barrierDismissible: false`，也没有「稍后再说」按钮）——
   门店只能强制结束进程。

2. **后台自愈永久停摆**：自愈有 `_syncing` 标志防止重入。若某次请求
   永久挂起，`_syncing` 永远为 `true`，之后每轮自愈都被
   「上一轮还没跑完」挡掉，**同步功能就此静默失效，且没有任何日志线索**。

**修复（已完成）**

- 新增常量 `httpTimeout = 20 秒`，设到 `connectionTimeout` 与 `idleTimeout`
- 每个请求的 `close()` / `drain()` / 响应体 `join()` 都包 `.timeout(httpTimeout)`
  —— `connectionTimeout` 只管「建连」，响应体读取仍需单独兜底
- `httpTimeout` 本身设得比 `httpTimeout` 单请求上限更短，保证总时长可控

## 🟠 中等：等待预算会被单次请求吃掉

**现象**

原 `_waitForPeerRowId` 的循环是：

```dart
while (true) {
  final rowId = await _findPeerRowId(...);   // 可能耗时 20 秒
  if (rowId != null && rowId > 0) return rowId;
  if (!DateTime.now().isBefore(deadline)) return null;
  await Future.delayed(peerWaitInterval);
}
```

deadline 只在**请求返回之后**才检查。加上 HTTP 超时后，
30 秒的预算实际会跑成 45 秒（20 秒请求 + 5 秒间隔 + 20 秒请求）。

**修复（已完成）**

- 请求前先算剩余预算，单次请求的超时取 `min(剩余预算, httpTimeout)`
- 轮询间隔也按剩余预算裁剪，预算耗尽立即返回
- 零预算时**不发任何请求**直接返回

**验证**

`deploy/verify_wait_budget.py` 用镜像算法跑了 5 个场景：

```
[OK] hanging requests: waited 30.0s within 30.0s budget (2 attempts)
[OK] slow requests: waited 30.0s within 30.0s budget
[OK] peer found on attempt 3
[OK] peer found on first attempt, no extra polling
[OK] zero budget returns immediately without any request
```

## 🟡 轻微：首启弹窗的等待时长过长

**现象**

首启弹窗调 `syncStoreName(name)` 用的是默认 `peerWaitTimeout = 5 分钟`。
弹窗不可关闭，门店点完保存就得干等 5 分钟。

**修复（已完成）**

新增 `firstRunWaitTimeout = 30 秒`，首启弹窗单独用短的。
名字已经存到本机，剩下交给后台调度器补同步 —— 用户体感从「卡死」变成「稍等」。
